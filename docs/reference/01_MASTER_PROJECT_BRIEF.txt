## 6. Design Direction and Tokens

The approved style is **editorial tactile warm naturalism**: organic, premium but approachable, trustworthy, and farm-to-home. Avoid generic neon quick-commerce styling, heavy shadows, glassmorphism, or unapproved redesigns.

Important values from `DESIGN.md`:

- Warm canvas/surface: `#FFF8F1`
- Secondary warm surface: `#FBF3E7`
- White content surfaces: `#FFFFFF`
- Deep green primary token: `#093521`
- Forest green action/component token: `#234C36`
- Soft green: `#DBF5D1`
- Harvest yellow: approximately `#EDE0A5` / `#EEE1A6` as defined by the design token and component notes
- Main text/deep text: `#1E1B14` / `#243126` as used in tokens/components
- Muted text: `#706F63`
- Subtle border: `#E5DDCF`
- Error accent: `#B42318` / `#BA1A1A` as supplied; centralize the chosen component value and document any token reconciliation.

Typography:

- **Literata** for display and editorial headlines.
- **Source Serif 4** for body text, labels and numeric/price details.
- Locate and bundle the approved font files if included and permitted. If missing, document the missing file and use a clearly temporary, documented fallback during scaffolding.

Layout and shape guidance:

- Mobile-first viewport range: 360–480 logical pixels.
- Standard phone gutter: 16 px.
- Product grid: two columns with roughly 12 px gaps.
- Product cards: roughly 16 px radius, white background, subtle border, square product image, pack size, product name, price and add/quantity controls.
- Inputs: roughly 12 px radius; modal sheets: roughly 16 px top corners; chips/badges use pill radius.
- Bottom navigation: about 64 px plus platform safe-area inset.
- Use low-contrast borders and subtle elevation. Do not use heavy shadow or blur.
- Respect iOS/Android safe areas, keyboard insets, device notches, and text scaling.

Implement the design tokens once in reusable Dart theme/constant files. Avoid scattering raw hex values and spacing throughout screens.

## 8. Frontend Behavior During Mock Mode

All visible primary controls must work with local mock behavior or show a clear not-connected placeholder. Keep fake behavior explicitly identified during development.

- Search filters/suggests mock products; recent/trending searches are tappable.
- Category/filter/sort controls update visible results and retain selected state.
- Product card, quick-view, detail page, variant selection, favorite and add-to-basket share a coherent product/cart state.
- Cart quantity, removal, coupon UI, delivery slot and displayed bill totals update consistently from mock data.
- Checkout validates required local inputs, then creates a demo/mock order only; it must not place a real order or call a payment gateway.
- Order list and detail use the same mock order repository. Reorder copies eligible items into the basket. Tracking timeline is simulated—not real GPS tracking.
- Profile and address edits update local mock state. Selected default address is reflected on related screens.
- Wishlist supports save/remove/move-to-cart using shared cart state.
- FAQs filter/expand. Support actions do not send real WhatsApp/SMS or place calls without a user-initiated OS handoff and valid implementation.
- Farm Assistant provides sample conversation behavior only and must not imply a live agronomist or AI service.
- OTP and location/service-area screens are UI/mock flows only until real providers and backend logic are approved.
- Empty, loading, error, unavailable, validation, and permission-denied states must be implemented as reusable patterns using the supplied state references.

Do not add real backend behavior, use real customer information, store secrets, or claim mock results are production transactions.

## 9. Future Odoo Integration Boundary

Odoo Community and PostgreSQL are the planned single business backend/system of record after the frontend is stable. Do not build a separate MongoDB database or separate FastAPI business backend for the target architecture.

Flutter must eventually talk to secure, approved Odoo-facing HTTP API endpoints. It must not connect directly to PostgreSQL or expose Odoo administrator credentials. Do not assume the Odoo version, installed modules, custom fields, API endpoints or authentication details until the actual Odoo environment is inspected.

Protect the mobile UI from internal schema changes by defining a stable API contract and a dedicated repository/API adapter layer. Where suitable, product attributes and supported checkout fields may be driven by server configuration, but only predefined safe field types should be rendered dynamically. Odoo remains authoritative for price, inventory, availability, taxes, discounts, payment status and order status. Server-side validation will be required during integration.

The current stage uses mock repositories only. Odoo integration comes after UI behavior is verified. Consider an OTA update option such as Shorebird later for compatible Dart/UI hotfixes; do not make it a dependency for initial frontend scaffolding or treat it as a substitute for stable API contracts. Native platform changes may still require store releases.
